# 技術的正確性と出典管理

## 主張を5種に分ける

| 種別 | 具体例 | 記述の指針 |
| --- | --- | --- |
| 確認した仕様 | 公式ドキュメントに記載されたAPI動作 | 仕様と適用バージョン・URLを示す |
| 実測・実行済み | ログ、ベンチマーク、テスト実行 | 実行環境・手順・結果を示す |
| 実装からの読解 | 関数の制御フロー、設定の意味 | 対象コミットやコードを示し、実測と呼ばない |
| 推論・仮説 | 失敗原因の推定 | 根拠と未検証の点を分ける |
| 評価・意見 | 選定理由、感想、トレードオフ | 筆者の判断と明示し、事実へ擬態させない |

## 情報源の優先順位

1. 実際のリポジトリのコード、設定、実行ログ、検証データ（対象の説明に限る）
2. 公式ドキュメント・仕様書・リリースノート・一次発表
3. 信頼できる二次資料（一次資料を確認できない理由も含む）
4. 個人ブログ・コミュニティ投稿（経験談や補助情報として）

一次資料であっても、記事の対象バージョンと一致するか確認する。検索結果の要約だけで詳細仕様を断定しない。ソース内容を引用する際は著作権・ライセンスを尊重し、長文転記を避ける。

## 実行可能性の基準

- コード例は「概念説明用」「抜粋」「コピペ実行用」「検証済み」を区別する。
- 本文に載せるコマンドを安全性の観点から読む。破壊的な操作、権限変更、ネットワーク公開、シークレットを扱うものは前提・リスクを明示する。
- 環境は記事で結果に影響する範囲（OS、ツール、主要バージョン、設定）を示す。根拠なく細かいバージョンを補わない。
- エラーと出力ログは、実際の証跡がないなら架空の「実行結果」として載せない。説明用の例示として明記する。
- パフォーマンスの比較は測定手順・ハードウェア・サンプル数・統計処理が不明なら一般化しない。
- 表現を改善する目的だけでコード・設定・API名・戻り値・ファイル名を改変しない。

## 書けない場合の処理

- ユーザーのメモに「動く」とあるが環境や証跡がない: 「筆者の報告」または「未確認」と明示する。
- 出典へアクセスできない: 推測して補完しない。必要なURL・仕様・実験を未確認事項として本文外に記す。
- 事実に矛盾がある: どちらかを勝手に採用せず、矛盾を説明する。
- 結果をまだ得ていない: 検証手順や期待値として書く。検証済みとは記さない。
