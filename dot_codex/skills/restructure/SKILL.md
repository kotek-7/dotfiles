# Restructure

成長したプロトタイプを、機能の置き場所、状態の所有者、依存方向が分かる構成へ再編する。既存の動作を保ち、次の機能追加が自然な場所に収まることを成果とする。行数削減やディレクトリ数を成果指標にしない。

## 作業範囲

「調査だけ」「方針だけ」なら読み取りと提案まで。再構成や移行の実装を依頼されているなら、調査、設計判断、実装、検証まで進める。設計を短く共有するために、許可済みの作業を再承認待ちにしない。対象や制約に重大な曖昧さがあるときだけ質問する。

技術スタックの再評価は行うが、変更の範囲はユーザーの指定に従う。UIの再デザイン、新機能、仕様変更、デプロイを再構成に混ぜない。Web以外でも適用し、言語やフレームワークの慣習に合わせる。

## 1. 実際の責務と結合を調べる

- プロジェクトの指示、Gitの変更状態、起動点、ビルド設定、実行環境、公開API、既存テストを確認する。並行作業や未コミット変更を保持する。
- `rg --files`などで対象を絞る。生成物、vendor、lockfile、大きな定数表は、手書きの複雑なロジックと区別する。ファイルサイズは調査の入口にとどめる。
- 代表的な操作を入口から結果まで追う。表示、状態遷移、業務ルール、通信、永続化、初期化がどこで混ざっているか、ファイルとシンボルで示す。
- importだけでなく、共有可変状態、グローバル変数、イベント、DOM参照、CSS、初期化順序による隠れた依存も調べる。既に良い境界があれば残す。
- 問題を「責務の混在」「状態の所有権」「依存の逆流・循環」「スタックとの不適合」に分ける。現在ある問題と、ユーザーが求めている今後の変更を根拠にする。

## 2. 挙動の基準を確保する

変更する範囲で維持すべき主要操作、入出力、公開API、URL、保存形式、エラー時の動作を押さえる。UIがある場合は表示、キーボード操作、フォーカス、必要な画面幅も含める。

既存の関連テストとビルドを実行し、変更前からの失敗を区別する。テストが乏しく、変更で壊れやすい処理には、公開された振る舞いや業務ルールを確認する小さなcharacterization testを先に加える。単純な移動のために、内部関数名やディレクトリ構造を固定するテストを増やさない。既知の不具合を無条件に仕様として固定しない。

UIは利用可能なブラウザ手段で変更前の主要フローと表示を確認する。実行環境が使えない場合は制約を記録し、可能な静的検証を進める。

## 3. スタックを選び直す

現状維持も選択肢に含めて、必要な範囲で比較する。

| 選択肢 | 判断の根拠 |
| --- | --- |
| 現行スタックで再構成 | 主な問題が配置、責務、状態の持ち方であり、現在の技術で明確に表現できる |
| 一部の仕組みを置換・導入 | ルーティング、状態遷移、通信、描画など、特定の仕組みに複雑さが集中している |
| 対象範囲のスタックを移行 | 現行方式では要求を扱いにくく、移行後に削除できる独自実装や結合が具体的に示せる |

候補ごとに、解決する問題、不要になるコード、新しく必要になる仕組み、移行コスト、実行・配信制約を確認する。「数千行だからReact」「流行しているから全面移行」を理由にしない。一方、既存技術を守るためだけに独自の複雑な仕組みを温存しない。

スタックを変更する場合は候補の公式資料とプロジェクトの実際のバージョン、ランタイム、配信方法を確認する。既存のパッケージ管理を尊重し、無関係な最新版への更新を混ぜない。調査できない互換性を確認済みとして扱わない。

フロントエンドの技術選定やHTML・JSからの移行では、[frontend-migration.md](references/frontend-migration.md)を読む。React採用は選択肢の一つであり、このスキルの前提ではない。

## 4. 機能の境界と依存方向を決める

実装前に、問題と移動先の対応、主要ディレクトリ、許可する依存方向、スタック判断、移行順序を短く示す。図の矢印はimportなどのコード依存を表すのか、実行時のデータの流れなのか明記する。全関数の設計書は作らない。

### Colocation

- 一緒に変更する機能のUI、状態、ルール、スタイル、専用ヘルパー、テスト、アセットを近くに置く。小さい機能は数ファイルでよく、最初から全機能に同じ階層を作らない。
- まず機能内に閉じる。複数の利用箇所で同じ意味・契約が成立すると確認できたものだけ、最も近い共通の所有者へ移す。形が似ているだけの処理を共通化しない。
- `components/`、`hooks/`、`services/`、`types/`、`utils/`への全体的な分類で、同じ機能を再び散らさない。既存フレームワークのルート配置や言語固有のモジュール規則には従う。
- 真に横断的なUIや基盤だけを共有する。`shared`や`common`は所有者不明の業務処理の置き場にしない。機能横断のE2Eは横断範囲を扱う場所に置いてよい。

### SOLIDを境界に適用する

クラス化や抽象層の数を目標にせず、関数、モジュール、コンポーネントにも適用する。

- **S:** 同じ理由で変わる処理をまとめ、表示変更、業務ルール変更、保存先変更を分けて扱えるようにする。一関数一ファイルを強制しない。
- **O:** 実在する変更軸にだけ、関数引数、合成、差し替え可能な実装などの拡張点を置く。仮想的な将来のためにプラグイン基盤を作らない。
- **L:** 同じ契約の代替実装は、成功結果だけでなく失敗、非同期処理、重要な副作用の意味も守る。満たせない実装を同じ抽象に押し込まない。
- **I:** 呼び出し側に必要なデータと操作だけを公開する。巨大なコンテキスト、ストア全体、万能サービスを配布しない。
- **D:** 業務ルールをUI、DB、ブラウザ、外部SDKの詳細から切り離す。境界が必要なI/Oは利用側の要求に合わせた小さな契約で受け取り、起動・接続箇所で具体実装を渡す。DIコンテナや全クラスへのinterface追加は不要。

### 依存と状態の所有権

- 起動・接続を担うコードは各部を組み立てる。業務処理をそこへ集め直さない。ルールや契約から起動コード、UI、具体的なI/O実装への逆流を避ける。
- 機能の外からは必要な公開口だけを使う。正当な機能間依存は明示して一方向に保つ。循環は責務、契約の所有者、連携箇所を見直して解消し、イベントバスで隠さない。
- 各状態に正本と更新責任を一つ定める。UIの一時状態、業務状態、サーバー由来データ、派生値を区別する。派生値の二重保存や双方向の同期処理を増やさない。
- 境界を越えて業務上の不変条件を変える操作は、意図の分かる関数やコマンドとして公開する。外部から内部状態を自由に書き換えさせない。単純なローカルUI状態までコマンド基盤に載せない。
- UI、サーバー、Worker、CLIなど実行環境が分かれる場合は、その境界も保つ。サーバー専用処理をブラウザに含めない。共用ルールは、UIや各環境のエントリーポイントを経由せず利用できる位置に置く。

## 5. 動く単位で移行する

1. 代表的な機能を選び、入出力、状態、副作用の境界を確定する。その機能が実際に動く経路を通して、新しい構成が役に立つか確認する。
2. 既存のルールを抽出し、呼び出し側を接続する。移動、挙動変更、技術変更を区別できる差分にする。単純な移動に不要なラッパーを追加しない。
3. スタック移行が必要なら、確認できた境界から置き換える。移行中に二つの実装が同じ状態や副作用を同時に支配しないようにする。
4. 呼び出し元、import、パス解決、テスト、ビルド、静的アセット、必要なCI設定を追従させ、対象の挙動を検証する。
5. 確認できた構成を残りの対象へ広げる。代表機能だけで止めず、依頼された範囲を完了する。
6. 不要な旧実装、依存、設定、互換用の中継を削除する。残すものには実際の利用者や移行上の理由、撤去条件を示す。

薄い入口と巨大な`useApp`、ストア、サービスの組み合わせに移しただけなら、責務分割は終わっていない。機能を変更するときに、その機能の近くで処理を理解できるかを見直す。

## 6. 完了を検証し、境界を残す

- 影響範囲のテスト、型検査、lint、ビルドなど、プロジェクトにある適切な確認を通す。追加したテストは移動後も意味を持つ振る舞いを検証する。
- importや実際の参照を調べ、循環、機能内部への不要な参照、実行環境の混在、旧経路の残存を確認する。path alias、再export、動的ロードも考慮し、文字列検索だけで完全性を断言しない。
- 既存のコンパイラやlintで重要な境界を低コストに制約できるなら活用する。構成整理のためだけに独自の汎用検査基盤を作らない。
- UI変更では主要フローと表示を再確認する。保存形式や外部契約を維持した証拠も確認する。ビルド成功だけで動作維持を断言しない。
- 今後の追加先、公開口、依存方向、状態の所有者、スタックの判断理由を既存の適切な設計文書に簡潔に残す。適切な文書がない場合だけ、小さな構成ガイドを追加する。

最終報告は、変わった責務と依存、スタックを維持・変更した理由、実行した検証、未検証事項を中心にする。実際に変更したファイルを示す。調査のみの場合は、実装済みと混同しないよう推奨案と次の作業を示す。
