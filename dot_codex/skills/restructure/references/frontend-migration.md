# フロントエンドの選定と段階移行

UI技術の選定や置換が対象の場合に読む。以下の構成例はReactを選んだ場合の一例であり、全プロジェクトのテンプレートではない。

## 採用する仕組みを絞る

| 現状の問題・要件 | 検討する方針 |
| --- | --- |
| 主に静的なページで、独立した操作が少数 | 現行HTMLとJSモジュールでの責務分割や局所的な拡張 |
| 手動のDOM更新が多数あり、画面と状態の同期が壊れやすい | Reactなどの宣言的UIへの移行。既存ページの一部への導入も比較する |
| 既にReactだが巨大なAppやフックに集中している | 機能と状態の所有権の整理。フレームワーク変更では何が解決するのかを先に示す |
| 画面遷移、データ取得、複雑な状態遷移の独自処理が肥大化 | 問題を担当する仕組みだけを比較する。router、query cache、状態機械などをセット導入しない |
| SEO、サーバー描画、静的配信、既存バックエンドとの統合が重要 | 配信方式まで比較する。UIライブラリの選択からSSRやサーバー追加を自動的に決めない |

JSからTypeScriptへの変更も、契約の確認に役立つか、既存コードとの共存や移行に何が必要かで判断する。React移行と同時の必須条件にはしない。フレームワーク、状態管理、CSS、ビルドツールの変更理由をそれぞれ説明できるようにする。

## 境界の例

```text
src/
  app/                 # 起動、ルート、依存の接続、機能間の連携
  features/
    cart/
      CartView.tsx     # 表示と操作の入口
      useCart.ts       # このUIに必要な状態・ライフサイクルだけ
      cart.ts          # 計算や状態遷移
      cart.test.ts
      CartView.module.css
  ui/                  # 業務固有の知識を持たない共通表示部品
```

必要なファイルだけ作る。小さい機能なら`CartView.tsx`内の局所的な処理で十分なこともある。保存や通信が必要になれば、その機能または適切な基盤の所有者に置く。各featureに一律で`domain/application/infrastructure`を生成しない。

この例のコード依存は`app → featureの公開口`、`UI → ルール`、`I/O実装 → 利用側の契約`となる。具体実装の選択は`app`などの接続箇所で行う。実行時にルール側が注入された保存処理を呼べても、ルール側からブラウザ保存実装をimportする必要はない。

公開口は外部から使う実際の関数やコンポーネントに絞る。`index.ts`は必須ではなく、全てを再exportするbarrelは作らない。安定したルールや契約をサーバーとも共有する場合は、ブラウザ専用のfeature入口から切り離す。

## HTML・JSからReactへ移す場合

1. 対象のHTML、DOM参照、イベント登録、状態、タイマー、通信、保存を追う。旧コードが暗黙に作っている初期値や起動順も確認する。
2. 計算や業務ルールをDOMから切り離す。JSのまま始めてもよい。変更前後で同じ入力に対する結果を確認する。
3. 既存ビルドに統合する方法を公式資料で確認する。ビルドがない場合は必要な最小構成を選ぶ。プロジェクト全体を新規テンプレートで上書きしない。
4. 一つの画面、ルート、または領域に描画の境界を置く。その領域のDOMと状態は新実装が所有し、対応する旧イベント処理とDOM更新を外す。旧コードによる二重更新を防ぐ。
5. 状態から表示を決め、操作を明示する。DOMから値を読み直して帳尻を合わせる処理、派生値の二重保持、巨大な`useApp`への移植を避ける。Effectは外部との同期に使い、単純な計算の代わりにしない。
6. 再マウントや画面遷移でイベント、タイマー、購読、通信の後処理が正しく働くことを確認する。移行前後の実装が二重送信や重複保存を起こさないようにする。
7. 主要操作を通してから残りを移し、不要になった旧入口、コード、依存を削除する。二つの方式を恒久的に保つ場合は、その境界と理由を明記する。

小規模で依存が把握できている場合は、領域ごとの共存より一括切替が単純なこともある。どちらでも挙動の基準と切り戻せる差分を用意し、段階移行のためだけの複雑な橋渡しを作らない。

## 移行で見落としやすい互換性

- **見た目:** CSSの読み込み順、cascade、フォント、アセットURL、レスポンシブ表示。配置変更とスタイル方式の変更を混同しない。
- **操作:** フォームの送信、Enterキー、フォーカス、ダイアログ、スクロール、入力途中の値、loading・error・empty表示。
- **URLと配信:** deep link、戻る・進む、base path、静的配信のfallback、既存サーバーのルーティング。
- **データ:** APIの入出力、保存キー、保存形式、既存データの読み込み、保存タイミング。移行に合わせて勝手にデータを初期化しない。

関連する項目を変更前後で確認する。見た目はブラウザで、ルールはテストで、配信設定は実際の起動・ビルド方法で確かめる。検証できていない範囲は明記する。
