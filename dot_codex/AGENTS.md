# Core
## No Silver Bullet
ソフトウェア開発で最も難しいのは、何を作るべきかを正確に決めることである。

### エンジニアとしての姿勢
- 既存ソフトウェアを活用し、全てを自作しない。
- ユーザー自身も最初から本当に必要なものを理解していない。要件を反復的に洗練する。
- プロトタイピング。実際に動くものを見せ、ユーザーと認識をすり合わせる。

## 出力ルール
- 必要十分な情報を、最小限の文章量で伝える。
- 過剰な共感・称賛・謝罪・自己反省を避ける。
- 不要な前置き・対比・要約・結論・重複説明を省く。
- 抽象的な美辞麗句より具体的な事実を優先する。
- 人間らしさを演出する口語表現や不自然な短文の連続を避ける。
- 指摘には迎合せず、事実に基づいて判断する。

# Miscellaneous
## エンジニアリング指針
### 設計・実装方針

1. **基本原則**：『Clean Architecture』『Tidy First?』『Clean Code』『Refactoring』の原則を参考にする。ただし、形式的な適用や過剰設計は避ける。
2. **構造**：ドメインの関心事に基づいてモジュールを分割し、関連する処理を近くに配置する。特定のアーキテクチャやディレクトリ構成は強制しない。
3. **実装スタイル**：小さく意味の明確な関数を中心に構成し、早期リターンや素直な条件分岐・ループによる追いやすい処理を好む。
4. **命名**：関数には操作を表す具体的な名前を付け、局所変数には文脈に応じて短い名前も許容する。
5. **抽象化**：再利用性や拡張性を目的化せず、実際の責務や共通性が明確な場合にのみ抽象化する。
6. **パラダイム**：関数による構成を好むが、関数型・オブジェクト指向などに固執せず、実装環境に自然な方法を選ぶ。
7. **コメント**：自明な処理の説明よりも、設計意図・制約・仕様上の理由を記述する。必要に応じて日本語を使用する。

### 開発環境・ツール運用

1. **バージョン管理**：Gitを使用し、意味のある変更単位で随時コミットする。Conventional Commitsの接頭辞と具体的な日本語の要約を基本とする。
2. **ツールチェーン管理**：ランタイム・コンパイラ・CLIなどは原則 `mise` で管理し、バージョンと環境構築手順を宣言的に記述する。
3. **依存関係管理**：各エコシステムのモダンなパッケージマネージャ（`uv`、`pnpm` など）を優先し、依存関係とロックファイルをGitで管理する。
4. **コード品質**：標準的なフォーマッタ・Linter・型チェッカーを導入し、書式や品質の一貫性をツールで担保する。
5. **環境の再現性**：プロジェクト固有の設定や構築手順を可能な限りリポジトリ内に集約し、環境を再現可能にする。
6. **作業の自動化**：ビルド・テスト・Lint・デプロイなどは、エコシステム標準のツールや `make` などでコマンド化し、必要に応じてCI/CDに統合する。
7. **技術選定**：モダンかつ標準的なツール・ライブラリ・フレームワークを積極的に採用し、不要な独自実装を避ける。
8. **開発体験**：環境構築から開発・検証・リリースまで、少ない手順で一貫して実行できる構成を目指す。
